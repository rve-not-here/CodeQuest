# CodeQuest challenge exploration

## Interpretation and assumptions

This is a renewed visual exploration of CodeQuest’s Challenge and Boss Challenge workspace, rather than another implementation report or a production redesign. The immediate context is a user who dislikes the previous Challenge workspace and explicitly prefers freeCodeCamp’s design. The relevant quality is its relationship between instructions, editable source, and visible results. Merely reproducing its colors, replacing the CodeQuest brand, or adding a generic IDE frame would miss the request. We need to show different interpretations of that working relationship so the user can select using real rendered evidence.

The audience is SEAIT programming students learning HTML through short lessons, optional Knowledge Checks, practice Challenges, and independent Boss Challenges. Students may be new to programming and repeatedly use the environment during an academic term. They need clear instructions, substantial editing space, obvious execution and submission controls, and feedback that relates to their source. They should not have to decode decorative terminal labels, secondary dashboard metrics, or an extensive navigation tree before writing code. The design needs to support deliberate work on laptops and a usable mode switch on phones. Visual identity comes from the task structure and typography, with restrained color and consistent controls.

We already have the repository, existing screenshots, a local prototype, and a preferred reference. Those resolve the usual discovery questions. No new photography or invented brand artwork is necessary for a programming tool. We retain the actual CodeQuest wordmark and terminal mark from the current student header. Prior sample names and portfolio content are explicitly prototype fixtures, not claims about a real learner’s academic record. User selection is still required before developing any direction further. All three drafts must be working standalone HTML files, with distinct composition and identical task content for fair comparison.

## Common content and behavior

Use CodeQuest with its existing >_ mark, primary navigation Dashboard / Learn / Boss Challenges, an unobtrusive learner profile, and an accessible link back to the lesson. The practice title is Links that make sense, within HTML foundations. The objective is Connect your profile to your work. The task is to create a profile with a clear introduction and a descriptive link to projects. Public requirements are a top-level heading, a short introduction, and a descriptive portfolio link. Explain the anchor element and href near the task. Do not imply that opening or reading content has recorded completion.

Use editable sample HTML showing Alex’s student developer profile, a heading, a short introduction, and an anchor whose href is missing. Include simple embedded CSS so Run produces an attractive yet modest actual portfolio preview. These are reused design-lab fixture contents, and must be labeled as examples. Run renders exactly the current HTML in a sandboxed iframe with no script permission. Run is ungraded. Editing must indicate unsaved source and stale output. Save draft stores source only in memory and says so. Submit demonstrates a pending/submission interaction, but must not grade code, award XP, write progress, or claim server confirmation. A clearly identified example feedback control can demonstrate a missing destination and return focus to source. Avoid alert() dialogs.

Boss mode, available with ?mode=boss or a visible practice/assessment switch, uses the same visual foundation. Its title is Build a student portfolio. It starts blank, removes practice hints and draft saving, displays the existing 70% threshold, and confirms submission finality with a native dialog. Do not invent a timer or hidden test cases. The demo must openly say no assessment is recorded. Blank retry and read-only recorded attempts belong to later authoritative integration rather than fake success in the first draft. Practice hint and solution can show existing cost information: hint 5 XP, solution 30 XP, failed submission penalty 10 XP. No actual XP changes occur here.

## Delivery and visual constraints

Each direction is one complete self-contained HTML/CSS/JS file, independent of React, CDN assets, or application imports. Opening it directly must work. Initial evaluation uses 1440 by 900 desktop, 1024 by 768 laptop, 768px tablet, and 375px phone. No permanent global sidebar. Different structural arrangements are required; a palette-only difference does not count. Use a visible code/editor label, Preview and Feedback areas, public requirements, persistent Run/Submit controls, and useful recovery placement. Do not wrap every pane in a rounded card. Prefer full-height editing, straight separators, intentional alignment, compact headers, and meaningful whitespace. Avoid neon, purple gradients, fake technical comments, XP stats walls, achievement decoration, or oversized marketing headlines.

On narrow screens use Instructions / Code / Output modes without destroying editor content. Critical actions remain reachable, and hidden panes leave the keyboard order. Use native textarea source editing or an equally accessible editor with an escape route. Controls should be at least 44px high, body copy at least 14px and preferably 16px on phones, metadata at least 12px, and text contrast at least 4.5:1. Include explicit labels, visible focus, reduced motion, and a polite atomic status announcement. Tab switches support arrow keys without overriding typing or editor shortcuts. No runtime errors or horizontal page overflow.

## Form questions

Role: a focused learning tool, not a marketing hero. Distance: laptop working distance and handheld phone. Temperature: calm, precise, encouraging without childish decoration. Capacity: a short task, three requirements, approximately twenty source lines, one rendered preview, and local feedback must fit a desktop viewport. Motif: the semantic connection from anchor source to its destination, expressed through the spatial relationship of task, code, and result. Every direction must state how its composition comes from this relationship. Preserve the previous prototype. Do not touch production code, dependencies, backend logic, database, or git history. Only write the assigned direction file. Parent will render, compare, and gather the user’s choice.
