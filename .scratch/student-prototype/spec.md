# Design spec — CodeQuest student interactive prototype (shared input for 3 directions)

## 1. What this is
A clickable high-fidelity prototype of the CodeQuest **student** journey, rebuilt from the real Laravel app (not a generic "learning dashboard"). It covers the authoritative learning flow from the master spec: Dashboard → Learning Path → Lesson → Knowledge Check → Coding Challenge workspace → Boss Challenge, with XP / Competency / Timeline consequences visible. The reference URL the user sent requires ChatGPT login (HTTP 401, verified with curl), so it cannot be scraped; this spec is grounded in `DESIGN.md`, `PRODUCT.md`, `CONTEXT.md`, `routes/web.php`, and the real Blade screens (`dashboard`, `learning-path`, `lesson`, `challenge`, `knowledge-check`), which is stronger context than the locked link.

## 2. Audience and scenario
Audience: beginner web students (HTML/CSS/JS from scratch) on desktop-first, plus teachers glancing at the same language. Scenario: a student opens the terminal, sees exactly what to do next, drills one mission, fails safely, retries, passes, earns XP, and sees the path unlock. Use happens in 10–60 minute sessions at ~1m laptop distance: type must stay legible, code must stay still (no CRT shimmer over editor), and every state must read without color alone. Keyboard works throughout; focus is always visible (cyan 3px).

## 3. Core content (same real content in all 3 versions, no lorem)
Screen A — Dashboard (command-first): kicker `SYSTEM 404 // STUDENT TERMINAL`, command title "Continue: HTML Fundamentals — Challenge 07: Fix the broken card", support copy "Server validates. Preview never counts.", primary CTA `RESUME CHALLENGE 07`, secondary `VIEW LEARNING PATH`. Status strip: XP balance 1,240 (link to xp-ledger), streak-free (never invent streaks), Competency HTML: developing, next Boss gate "2 missions to Boss Challenge". Activity list: mission_completed +120, wrong_submission -10, hint_used -5 (auditable ledger language).
Screen B — Learning Path rail: Course HTML Fundamentals 68%; Section 03 "Styling with CSS" header; nodes: 05 completed (phosphor check), 06 completed, 07 current (amber dot + pulse), 08 available (cyan open circle), 09 locked (dashed x); Boss Challenge milestone card at rail end (amber sigil, `LOCKED — finish required missions`).
Screen C — Challenge workspace (3 panes): brief pane (title, difficulty MEDIUM amber badge, +120 XP, requirements list R1–R3, broken-code note), editor pane (dark CodeMirror-like pre block with editable textarea reality, line numbers, draft status "DRAFT SAVED 12:04"), preview pane (white sandboxed render of a card), toolbar (RUN PREVIEW / SUBMIT FOR VALIDATION / HINT -5 / REVEAL -30), assistance drawer with hint cost language and wrong-submit -10 warning. Knowledge Check interlude modal: 2 questions, cyan option rows, submit bar, score block.
Screen D (compact footer strip): timeline + recommendations + achievements links, so the prototype proves the wider system exists.

## 4. Emotional tone and keywords
Operational, calm, serious-playful: "academic emergency terminal". Quiet confidence, never hype. Keywords: disciplined, legible, phosphor-lit, engineered, honest (preview ≠ proof, costs stated upfront). Temperature differs per direction (see §7) but all stay inside System 404 fiction: repair the system by learning.

## 5. Output format and size (mandatory, identical across 3)
Clickable single-file HTML prototypes (pure HTML/CSS/vanilla JS, no build, no external images, system monospace only), viewport-first **1440×900**, responsive down to 360px (stack panes, rail full-width). Three files: `.scratch/student-prototype/design-demos/roulette.html`, `reference.html`, `designer.html`. Each file contains all 4 screens switchable via top nav tabs (Dashboard / Path / Challenge / Check) as independent mini state machines: tabs switch, Submit runs fake server validation (one fail then pass to demo safe-fail), Hint deducts demo XP counter, modal opens/closes. Readability floor (no exception): body ≥14px, meta ≥12px, contrast ≥4.5:1, first viewport has one explicit visual anchor (command title / rail head / workspace context bar). No page numbers on screens.

## 6. Constraints (hard)
Keep terms Mission/Challenge/Assessment/Boss Challenge/XP/Competency/System 404. Keep server-authoritative language (preview never counts; solution_code and validate_rule never shown). No streaks, leaderboards, hearts, or invented testimonials/stats. No glassmorphism, no purple-blue gradient, no pill controls, no pixel-art chrome, no decorative pixel fonts, no emoji icons. No curves on workspace panes. Honors `prefers-reduced-motion`. No external assets: everything inline, double-click to open via file://.

## 7. The three interpretation logics (same content, different skeletons)
Logic 1 Roulette (#6 Bold Big-Type Editorial, seconds 25 → 25%20+1=6): fashion-poster treatment of the terminal — giant condensed headline occupying half the viewport, rule-line grid, black/white + one phosphor accent, numbered sections 01–04. Skeleton differs: poster hero + stacked full-bleed bands, rail rendered as oversized numbered index list.
Logic 2 Real reference (freeCodeCamp practice layer + boot.dev progression layer, the two named influences in the master spec): densest and most familiar — left sticky rail nav + command band + 3-pane workspace exactly like freeCodeCamp's brief/editor/preview with boot.dev-style sequential nodes and XP costs. Skeleton differs: classic app shell, sidebar-driven, highest information density.
Logic 3 Best designer (Teenage Engineering industrial minimal — engineered squares, 2px radii, one voice, restrained glow): quietest, most engineered — top command bar + centered 50rem vertical signal rail as hero, workspace as one instrument with shared borders, a single 120%-detail signature (the amber current-node pulse + phosphor command edge). Skeleton differs: centered instrument column, minimal chrome, maximal whitespace-as-composition.

## 8. Image needs (Phase 3.5 checkpoint)
Decision: NO photographic/illustrated images required. Honest test applied per screen: removing any picture loses zero information — this is a tool UI (dashboard/rail/editor), not editorial content about a place/person/product. Therefore no Wikimedia/Unsplash fetching, no AI generation, no base64 payload. All visuals are CSS/SVG: square markers, signal dots, sparklines, code blocks. This also keeps single-file file:// delivery intact and avoids stock-inspiration slop.

## 9. Visual motif hypothesis (form grows from content)
The motif is the **signal rail**: a vertical 1px phosphor line with square state markers that runs from dashboard (progress) through learning path (nodes) into the challenge (requirements R1→R3 as rail stops). It is the one element no other topic would produce, and each direction must render it differently (poster index / app sidebar rail / centered instrument). Form statement each delivery must carry: "form comes from the progression rail, the vidé of sequential unlock".
