# Services

## Assessment eligibility: all course missions complete, empty sections vacuous
Assessment eligibility (AssessmentService::isEligible): a course is eligible only when the student has a Progress row for every mission in the course (queried via course->missions(), the full hierarchy-derived set), and the course has at least one mission. Query all course missions, NOT per-section — an empty section is vacuous and cannot mask an incomplete mission elsewhere, but a course with only empty sections (zero missions) is not eligible. Server-determined only; no client count/flag trusted.

## Assessment attempt ownership-gated serialization; one-row-per-attempt begin
Assessment attempt access is enforced in the service, never the view: AssessmentService::hasAccessToAttempt() (attempt.user_id === user.id) gates attemptResult(), which throws AssessmentAttemptAccessDeniedException for a non-owner. A student sees their own code/score only because they own the row — do not rely on view omission. One row per attempt lifecycle: beginAttempt() creates 'started' or transitions 'available'->'started', resumes an already-started attempt, and throws AssessmentAttemptNotRetryableException for submitted/evaluated/passed/failed (retry is US-409).

## Assessment submit: ownership first, lifecycle guard, no client-authoritative fields
Assessment submission (AssessmentService::submitAttempt): ownership gate runs FIRST (hasAccessToAttempt, throws AssessmentAttemptAccessDeniedException for a non-owner, attempt row untouched), then the lifecycle guard (only status 'started' accepts a submission; otherwise AssessmentAttemptNotSubmittableException). The method accepts only code against a user-owned attempt; it has no score/pass/fail/XP/completion/eligibility parameter, so none can flow from the client (§11/§43/§45). It records code, status 'submitted', submitted_at, and leaves score/passed_at null. Scoring is US-407; submission does not evaluate.

## ValidationService rules-string core; proportion-of-rules evaluation scoring
ValidationService::validateRules(string $rulesJson, string $code) is the generalized pattern engine (missions AND assessments). validate(Mission, code) delegates to it. Result shape is {passed, failures, total} — 'total' feeds the assessor's proportion-of-rules score. Assessment evaluation scoring (AssessmentService::evaluateAttempt): score = round(passedRules/total * 100) vs passing_score, computed only after an ownership gate and a 'submitted'-state guard; evaluates directly to 'passed'(passed_at set) or 'failed'; never persists 'evaluated'; a zero-rule assessment scores 0 and never passes. Code is pattern-matched only, never executed.

## Evaluated attempts immutable via services; fillable mass-assignment risk for US-413
An evaluated assessment attempt (passed/failed) is immutable through the service layer: evaluateAttempt() is the only writer of score/passed_at and the final status, and its 'submitted'-only guard plus begin/submit state guards make re-evaluation, resubmission, and re-begin all throw AssessmentAttemptStateException. The AssessmentAttempt #[Fillable] still lists score/status/passed_at, so this guarantee holds only while services are the sole writers and no controller ever feeds a request payload into ->update()/create(). When HTTP routes arrive (US-413), guard against mass-assigning those fields from client input.

## Assessment result fields guarded; services assign them directly, factory forceFills
AssessmentAttempt #[Fillable] excludes score, status, and passed_at — the result fields. Services set them only by direct attribute assignment + save() (begin sets status, submit sets code/status/submitted_at, evaluate sets score/status/passed_at); no create()/update() array includes them, so a future Attempt::create($request->all()) cannot mass-assign a result. AssessmentAttemptFactory overrides newModel() to forceFill so guarded fields still work in trusted test fixtures.

## Assessment retry = fresh row after pass or fail; US-410 completion needs the has-ever-vs-latest decision
Assessment retry (AssessmentService::retryAttempt, US-409): opens a FRESH row in 'started' with null code when the latest attempt is 'failed' or 'passed' (retry after pass is confirmed allowed), leaving the prior row as history. Refused with AssessmentAttemptStateException when no prior attempt (noAttemptToRetry) or while a latest attempt is available/started/submitted. Same isUnlocked gate as begin. latestAttemptFor already returns newest-by-id; attemptResult is per-row ownership-gated, so neither needed changes for history rows. CARRY-FORWARD for US-410: because a passed attempt is no longer terminal (retry-after-pass allowed), 'course complete' must define whether it keys off 'has ever passed' or 'latest attempt passed'.

## Course complete = has ever passed the assessment (hasPassed, history-based)
US-410 RESOLVES the completion carry-forward: course complete = the student has EVER passed the course's assessment (AssessmentService::hasPassed reads attempt history for a status='passed' row on this assessment/user). A later retry — pass or fail — never un-completes the course. DashboardService::currentCourse() (injects AssessmentService) returns the first active course (in order_num, skipping zero-mission courses) whose assessment has not been passed; finishing all missions only unlocks the challenge, it does not complete the course. All completion/usages (currentCourse, next-course unlock, assessment XP) MUST key off hasPassed(), never latestAttemptFor().

## Assessment XP awarded once per course pass (history transition, not status)
US-412 carry-forward (assessment XP not yet implemented): XP awarded for the ORIGINAL assessment pass stands permanently. A later retry attempt — pass or fail — never reverses, duplicates, or re-awards that XP. The XP award is keyed off the same history predicate as completion (AssessmentService::hasPassed), so awarding only when hasPassed() transitions false->true (i.e., no passed row existed before evaluation) prevents repeat-award on a retry pass. Do not award on 'passed' status alone.

## Next-course unlock is derived from currentCourse(); terminal course yields null, tested
US-411: there is NO per-user next-course unlock mechanism — no unlock table, field, or route, and none should be invented. Passing a course yields a passed attempt row, which flips AssessmentService::hasPassed() → DashboardService::currentCourse() skips the completed course and hands over the next active course in order_num (§19 sequential, no branching; the method takes no request input, so a client cannot select an arbitrary next course). 'locked'/'draft' courses are filtered out by status, never surfaced as current. Final course in the sequence: currentCourse() returns null → dashboard renders "Course complete" and LearningPathService::nextMission() (which resolves its default course via currentCourse) returns null — the defined, tested "no invalid next-course dependency". Zero-mission active courses are skipped (never completable, would strand the student).

## Assessment XP awarded inside evaluateAttempt, atomically, on first-pass transition only
US-412 EXPANSION of the XP rule: AssessmentService::evaluateAttempt awards the Boss Challenge XP (XpService::awardAssessmentPass, TYPE_ASSESSMENT_COMPLETED, amount = ASSESSMENT_PASSED_AMOUNT constant = 100, a named product decision). It runs INSIDE evaluateAttempt (not in a future controller) so no caller can forget the award; it is atomic with the verdict (single DB::transaction around save() + award). The one-time check reads the pre-state via $this->attempts($assessment,$user)->where('status','passed')->exists() BEFORE writing this attempt as passed (same history predicate as hasPassed): award only when $passed && !$hadPassedBefore. XpService::awardAssessmentPass is ALSO idempotent at the ledger (assessment_completed row exists check) — belt and braces. Repeat pass or failed retry never re-awards or reverses, ever.

## Progress overviews reuse the build() traversal, never re-derive counts
CourseProgressService (US-502) derives course state by consuming AssessmentService::hasPassed()/isUnlocked() + DashboardService::courseProgress()/currentCourse(); SectionProgressService (US-503) consumes LearningPathService::build() for per-section mission counts. The section hierarchy traversal (course->section->mission, per-mission Progress rows) lives in LearningPathService — do not write an independent aggregation loop when adding another progress overview. Section state labels: EMPTY (section with zero missions, never masks other sections) / DONE / IN PROGRESS / NOT STARTED. Never repeat a flat course-level percentage per section.

## Continue Learning priority: mission, then course; never the assessment
ResumeService (US-504) resolves "Continue Learning" for the dashboard. Priority: (1) unresolved mission via DashboardService::nextMission() (drafts first, then course order) with its section as context; (3) course-level when every mission is done but the Boss Challenge is outstanding — that CTA routes to learning-path, NEVER assessment.show (the challenge keeps its own Assessments entry point). An independent "current section" branch is unreachable: nextMission() already lands in the section with unfinished work, so a mission target always exists iff any section has work left. section can be null (missions may have no section_id). Resume must never be random, never deep-link the assessment, never skip incomplete work.

## Unified Learning Timeline: compose from existing records, never a new event table
TimelineService (US-505) composes beats from authoritative rows only: Activity (learning types, mission_completed + wrong_submission), XpTransaction (hint_used, solution_revealed, assessment_completed only), AssessmentAttempt (terminal passed/failed only), and Progress-derived section-completion beats timed at the last mission finish. Do NOT re-emit mission_completed/wrong_submission from the XP ledger (Activity already owns them — double-counts). Course completion is the Boss Challenge pass/award beat (US-410 hasPassed), not a synthetic row. Sec 51.0: login/logout Activity is filtered out — auth-boundary bookkeeping, no learning state.

## XP ledger display read: transactionHistory is the only student-facing read
US-506: student-facing history comes ONLY from XpService::transactionHistory(User, limit=30) → Collection of {amount, direction, reason, source, at} rows, newest first, no internal DB ids. The balance shown on the page must always come from balance() (the ledger sum) — never add a second authoritative balance. Direction is the action's intent (DEBIT_TYPES = wrong_submission, hint_used, solution_revealed), NOT the sign of the amount: a wrong-submission penalty clamped to a 0-amount row is still a debit. `at` is Carbon::parse(created_at).

## evaluateAttempt missing-assessment null guard has its own test
AssessmentService::evaluateAttempt throws InvalidArgumentException('references no assessment') when $attempt->assessment is missing (added as a US-505 typing side effect). The path is security-critical (US-407/408), so it must stay covered: test_evaluate_throws_when_the_attempt_has_no_assessment_reference in tests/Unit/AssessmentAttemptTest.php exercises it via setRelation('assessment', null) on an owned submitted attempt. Do not delete the guard or the test.

## Competency: per-course skill area, monotone 4-state ladder, no XP
US-507 (confirmed mapping): one competency per ACTIVE course with >=1 mission, named from course.type (html->HTML, css->CSS, js->JavaScript). Zero-mission courses never render; locked/draft excluded. Small monotone ladder, evaluated in order: DEMONSTRATED (all missions done AND hasPassed), PRACTICING (done*2>=total OR attempts>0), DEVELOPING (done>0 OR wrongSubmissions>0), NOT STARTED. Percent comes from DashboardService::courseProgress() (computed, never hard-coded). XP points play no role; the only wrong-submission signal reads the404_xp_transactions type=wrong_submission rows as a per-mission engagement journal (mission_id -> course), amounts never consulted. Monotone because both DEMONSTRATED inputs are history (Progress never deleted, hasPassed reads history) — a failed retry after a pass never downgrades.

## Competency attempts>0 disjunct: defensive, covered via direct manipulation
PRACTICING gate: `done*2>=total || attempts>0`. The attempt disjunct is unreachable through normal flow: beginAttempt/retryAttempt require isUnlocked->isEligible (all missions done), so any attempt row implies done==total, which makes the first disjunct true. It is a defensive completeness branch (only decisive under content drift — mission membership of an active course changing post-attempt, no such mutator exists). Keep it; its isolated test reaches the branch by direct data creation (factory attempt row with zero completions, bypassing the unlock gate) — same pattern as the US-505 null-guard test.

## AchievementService: server-side-only, idempotent awards
AchievementService::award(User, slug) is the sole write path; triggers are only evaluateMissionCompletion (after Progress::create inside the MissionService transaction) and evaluateAssessmentPass (first-pass branch of evaluateAttempt). It throws RuntimeException when the slug is absent from the catalog (fail-loud; the catalog is system-managed via AchievementSeeder running the four AchievementService::SLUG_* consts). The unique (user_id, achievement_id) constraint on the404_user_achievements is the idempotency backstop. No route/parameter can award an achievement. streak_3 = distinct calendar days of completed the404_progress >= 3; full_clear excludes active courses with zero missions or no assessment.

## RecommendationService composes ResumeService; review queue = Option B + restriction C
US-509: recommendation slots 1/2/4 are the THREE states of the shared ResumeService resolution (at most one fires): slot 1 = resume 'mission' on a started course; slot 2 = resume 'course' (all missions done, challenge outstanding) and MAY deep-link assessment.show — unlike ResumeService's US-504 no-assessment-link rule; slot 4 = resume 'mission' with course untouched AND an earlier active course passed (after-completion framing, links learning-path). Never re-derive the student position. Review queue (slot 3) is the only new resolver: completed missions (restriction C — in-progress work stays in slot 1) with >= 2 wrong_submission rows (threshold) in the last 14 days (window, inclusive at exactly 14 days), ordered by most recent wrong submission, capped at 3. Order: slot 1/2 position first, then review, but review before slot 4. Cards are display-ready arrays {slot, title, subtitle, href, cta}.

## StudentService (US-602) composes Phase 5 services; never re-derive formulas
StudentService builds the teacher student list by composing CourseProgressService::overview (states/progress), AssessmentService::isUnlocked/hasPassed semantics via currentCourse(), CompetencyService::overview (counts per state), and DashboardService::recentActivity/currentCourse — no teacher-specific copies of their formulas. Status filter keys are 'in_progress'|'ready'|'completed' (no current course = completed/ALL CLEARED); a current course's state is only ever IN PROGRESS or READY (completed courses are skipped by currentCourse()). Ordering: compute rows for every matching student, apply derived filters, then paginate in memory (LengthAwarePaginator; PER_PAGE=10). The ATTN column is a US-608 placeholder — do not implement attention logic here.

## StudentService full-table computation before pagination is a tracked §45.0 risk
TRACKED RISK (US-602, decided at 24-student scale, spec §45.0): StudentService computes rows for EVERY matching student in memory (CourseProgressService::overview + CompetencyService::overview + isUnlocked + recentActivity per student, ~25-30 queries/student) before slicing to a page. Deliberate and acceptable at the current roster — verify-in-memory is correct-by-construction because current-course filters are derived, and the spec's own example scale is fine. This is a NAMED, TRACKED item for the final Phase 6 report (same rigor as the US-511 drift and mobile-width deferral, not a passing note): if the roster grows, revisit BEFORE it becomes a real cost — move the two derived filters (current-course id, progress status) to stored/DB-computable form or bulk-paginate, and must preserve the derived filter semantics (currentCourse = first active course skipped by hasPassed, in_progress/ready/completed statuses). Do not silently refactor this without the user's knowledge.

## TimelineService::feed() (US-606) parameterizes the shared compose over a student set
The teacher feed is the SAME beat composition as the student timeline — TimelineService::feed() calls the same private compose()/sourcesFor() as events(), never a second composition mechanism. API: feed(?Collection $studentIds, ?int $courseId, ?string $type, Carbon $from, Carbon $to, array $paginatorQuery) → LengthAwarePaginator (FEED_PER_PAGE=30), beats carry user=>{id,username}. Volume sources run ONE query across the set (whereIn user_id) with student/type/date filters pushed down into SQL; assessment attempts are few rows (windowed in memory, beat time = passed_at vs submitted_at per status). Section beats run the per-student build() pass — bounded to students with progress inside the window — and are the ONLY per-user work. Course filter DROPS the Activity source (the404_activity carries no course link; exclude, never mis-attribute) and pushes course_id into xp (mission.course_id OR assessment.course_id) and assessment (assessment.course_id) + section (section->course_id). Window defaults: missing to => today, missing from => to−DEFAULT_WINDOW_DAYS (14), anchored in ActivityFeedRequest::prepareForValidation; the SPAN is capped at MAX_WINDOW_DAYS (90) in ActivityFeedRequest::withValidator (a wider client-supplied range is rejected before any query — the window bounds the in-memory slice, so the window itself must not be client-widenable). TRACKED RISK (§44/§45): beats are sorted+paginated in memory because sources are heterogeneous; the computed set is bounded by the default window + SQL pushdown + the 90-day cap. Revisit before volume grows (page windows or a persisted beat projection — keep compose() as the single vocabulary).

## CourseAnalyticsService (US-607) aggregates in SQL, reuses verbatim bucket predicates
CourseAnalyticsService::overview() computes fleet metrics at the SQL level (GROUP BY over the404_progress / the404_assessment_attempts), never per-student PHP fan-out — US-605's no-duplicate-formula verdict applied to the whole fleet. Bucket vocabulary is identical to the student-facing services: COMPLETED = hasPassed (any historically 'passed' attempt), READY = isUnlocked (all missions done AND assessment active), in-progress = any Progress row, and NOT-STARTED = fleet minus the engaged union (four buckets sum to fleet). Courses universe = status 'active' with >=1 mission, ordered by order_num; locked/draft/zero-mission are excluded. pass_rate = distinct students with a passed attempt / distinct students with a terminal (passed|failed) attempt, null when no terminal attempts exist; avg_completion = mean of per-student rounded percent, over engaged students only, null when none. The completion distribution is an int-indexed 0..4 list (never string band keys — PHP numeric-string key coercion), zipped against DISTRIBUTION_BANDS in the view.

## AttentionService: absolute day arithmetic, no composite/or signs
US-608. Carbon 3 diffInDays is signed, so day windows are computed as abs(now startOfDay minus target startOfDay). Attention signals are an OR-union of six independent flags over the student's CURRENT course only (boss_fail, repeat_fail, low_performance, stalled, inactive, never_started), each with its own constant and evidence string; there is no composite signal and no grading of severity. Engine deadline math lives in EngineService; never duplicate it here.

## Fleet pages aggregate in SQL; equivalence test is the proof
Fleet-scoped pages (CourseAnalytics, Attention) must do the fleet math once in grouped SQL (missionCounts, passedCoursesByUser, progressByUserCourse, attemptsByUserCourse, lastEventsByUser) and never per-student child queries, replicating the US-602 no-fan-out constraint. The attention equivalence test re-derives every student's signals from student-facing services modulo abs-day rounding and asserts an exact match — a formula-duplication break is caught, not asserted away.

## UserService stays the sole user write path; update carries guarded role/status changes (US-704)
UserService (US-703) is the admin user directory + the ONLY write path for admin user creation/editing. Server-side search/filter/paginate always (never full-table-to-JS). 'Last activity' MUST come from TimelineService::events per user (same beat vocabulary), never a new activity mechanism. Create/update are whitelisted: create sets username/name/role/password only (status stays on column default, operator unreachable via CREATABLE_ROLES = student/teacher/admin); update sets username/name, re-hashes password only when non-empty, and since US-704 also applies optional role/status. Role changes validate against ROLES (student/teacher/admin/operator — the FULL set, operator INCLUDED on existing accounts) and status against active|inactive. Update guards run BEFORE any write (§13): an admin cannot demote/deactivate THEMSELVES, and no change may remove an active admin (target admin+active with role changed away from admin or status->inactive) while the active-admin count is <= 2. Every refusal writes a 'failed' AdminAuditService::record() row (action user.role.change / user.status.change) then throws UserProtectionException; successes write 'success' rows; an unchanged role/status writes NO row. Create never takes status input and stays operator-free. There is NO delete path — deleting accounts is deliberately out of scope (§14/§5, educational records preserved).

## CourseService is the sole catalog write path; status is an access gate that seals use without rewriting progress (US-705)
CourseService::update() (US-705) is the ONLY write path for course fields and status; catalog ordering uses order_num as the single key (CourseService::ordered()). course.status (STATUSES = active|locked|draft) is an ACCESS GATE (confirmed by the user): 'locked' and 'draft' seal the course's missions (MissionController::ensureCourseActive aborts 403 on show/submit/draft/hint/reveal) AND its Boss Challenge (AssessmentService::isUnlocked requires course.status === 'active', surfaced as "Challenge sealed"), so a directly-URL'd mission can no longer accrue progress, XP, or achievements under a sealed course. Locking also removes the course from every status='active' consumer (DashboardService::currentCourse, CompetencyService, CourseAnalyticsService universe, AchievementService full_clear, RecommendationService, AttentionService). Progress recorded BEFORE the seal is preserved; only NEW use is blocked. Audit: status changes record 'course.status.change' ("Status changed: active → locked"), field changes 'course.update' with a "field → 'value'" summary, no-op round-trips write NO row, out-of-allow-list values record a 'failed' row then throw InvalidArgumentException (refuse() before any write, mirroring UserService). Request validates first; the service re-validates as defense-in-depth.

## SectionService sole write path; sections have no status and no status gate (US-706)

Do not add a section-status gate or a section-status column to this hierarchy.

## AdminMissionService sole mission write path; missions have no status and points are never retroactive (US-707)
AdminMissionService (US-707) is the ONLY admin write path for mission rows. DIFFICULTIES = EASY|MEDIUM|HARD; forCourse() orders by order_num then id. Do not add a mission-status gate or column, and do not recompute historical Progress/XpTransaction/Activity rows on a points edit.

## System status reads config only through a SAFE_CONFIG_KEYS allowlist
US-711 /admin/system (SystemStatusService) is the one place Phase 7 surfaces infrastructure state. Every config value it may display must pass the private safeConfig() gate, which throws on any key outside SAFE_CONFIG_KEYS (app.name/env/debug, logging.default only). Adding a secret-key read requires adding it to that constant — the deliberate review point. DB connectivity is a REAL getPdo + SELECT round trip (caught, never echoing PDO exception text; DSN fragments can leak through it), migrations status is read-only table peeks, and storage checks are filesystem stats. Never widen the surface casually.

## NotificationService reads are ownership-gated by the authenticated user
Notification read path is the ownership-check mechanism (US-801): every method is keyed by the authenticated User, no method accepts a target-user identifier, and single-notification lookups (findForUser) resolve only rows already scoped by user_id — a foreign or nonexistent id is indistinguishable (null). belongsTo(User, Notification) is the explicit ownership predicate, the same shape as AssessmentService::hasAccessToAttempt. Never add a method that resolves a notification outside the caller's user_id; producers that create rows land in later stories.

## Notification center + read-state mutations stay inside the user-scoped service
US-802/803 built on the US-801 mechanism: forUser now returns a LengthAwarePaginator (FEED_PER_PAGE=30, in-memory page slice of the caller's own rows); unreadCount is a SQL COUNT over the (user_id, read_at) index with the read-state filter pushed down (never a PHP collection filter); markAsRead resolves through findForUser then sets read_at directly + save(), so a foreign/nonexistent/already-read row is one identical idempotent false no-op and read_at is never rewritten or mass-assigned; markAllAsRead is a user_id-scoped bulk update returning the changed-row count (0 on re-run). Never add a method that resolves or mutates a notification outside the caller's user_id.

## Notification producer contract: route-name payloads, TYPE_ROUTES allowlist enforced at write AND read
US-804/805. create() is the only row writer; data is always a route NAME + params, never a URL. create() throws InvalidArgumentException on any route not on the type's TYPE_ROUTES allowlist (registered before a producer lands), on an unknown named route, non-array params, or non-scalar params. linkFor() re-applies the same allowlist and returns null on any mismatch, so a DB-tampered row renders no link. dedupe pre-check alreadyProduced() runs inside the caller's transaction; the unique (user_id, dedupe_key) index is the backstop. New producer types must register their destination route in TYPE_ROUTES first.

## Event producers: same-transaction create, first-pass-only transitions, derived unlock predicate
US-804/805. Producers call NotificationService::create() INSIDE the same DB::transaction as the state change (a rollback removes the notification, §19). Dedupe keys: mission_completed:{mission_id}, assessment_unlocked:{assessment_id}, assessment_passed/failed:{attempt_id}, course_completed:{course_id}, next_course_unlocked:{next_course_id}, achievement_earned:{achievement_id}. Course/next/assessment-unlock fire only on FIRST-pass transitions (pre-state captured before the write), keyed off hasPassed history — a retry pass never re-fires them. AssessmentService::firstNotPassedCourse() mirrors DashboardService::currentCourse (cannot inject it — cycle, same precedent as CourseAnalyticsService); the feature tests tie the two results together as the equivalence proof.

## Teacher attention notifications: change-driven + 24h cooldown, single signal source
US-806. AttentionNotificationService::syncFor($teacher) writes teacher_attention rows (dedupe null, frequency-governed) lazily on GET /students. Two INDEPENDENT gates, both tested: (1) change vs data.signals of the teacher's latest row per student — emission only when the ordered signal set differs; (2) 24h cooldown — suppresses emission regardless of change, but a real change stays pending and emits once the cooldown lifts (never lost). The signal set is stored as a server-authored auxiliary data key (data.signals, student under data.student); params stays [] so the rendered link is the plain /needs-attention route with no per-student query parameter (which would 403 the page's five-spelling guard). Recipient is the requesting user only; a student never sees these rows. Reuse AttentionService::list() verbatim — never a second attention rule set; the acknowledged cost is that /students computes the list twice (KPI + sync).

## Notification producer contract extension: server-authored auxiliary data keys
Since US-806, NotificationService::payload($route, $params, $auxiliary) accepts server-authored auxiliary keys and create() preserves them (data = {route, params} + auxiliary) via the same allowlist+route-name guard. This is how recurring/frequency-governed notifications store their change-detection state (e.g. teacher_attention stores data.signals + data.student). linkFor() still reads only route/params, so auxiliary keys never affect the rendered href. Only trusted producers construct payloads; never let client input shape auxiliary data.

## AnnouncementService lifecycle: first-publish-only fan-out
Announcement lifecycle: create always lands draft (status never client-supplied); publish sets published_at once and fan-outs exactly once (one system_announcement Notification row per active recipient, dedupe_key "announcement:{id}", route notifications); editing a published announcement never re-notifies; archiving is silent (no audit, no fan-out); archived is read-only; double-publish/archive-of-draft refused. Operator excluded from every audience; the publishing admin matches 'all'/'admins' like anyone else. Guard-refusals record a failed audit row BEFORE throwing, outside any transaction; success audit + fan-out inside one DB::transaction. Audience→roles: all→[student,teacher,admin], students→[student], teachers→[teacher], admins→[admin]; recipients must be active.

## StudentReminderService: change-driven reminder producer, lazy on GET /dashboard
US-809: syncFor(User) (student-only no-op otherwise, one DB::transaction) emits DRAFT_REMINDER (3 then 7 untouched days, monotone per mission via data.stage — max 2 rows per draft) and one LEARNING_REMINDER whose snapshot {course, kind} is change-driven: stalled (using AttentionService::STALL_DAYS verbatim) before unlocked-but-unattempted challenge (AssessmentService::latestAttemptFor === null). Reuse DashboardService::currentCourse — never a parallel course derivation (acknowledged double traversal, like US-806). Exclusions: sealed/locked/draft courses, zero-mission courses, completed missions (draft guard), already-attempted challenges. EnsureUserIsActive keeps inactive accounts away before the controller.

## ClassroomAccessService is the single visibility authority; ClassroomService the sole write path
Classroom / Enrollment Authorization: ClassroomAccessService::scopesFor($user) returns {studentIds, courseIds, byStudent}, where byStudent maps each monitorable student to their teacher-shared course set — course-level scoping (a student with shared classrooms is visible only for exactly the courses shared with this teacher). A teacher's scope = students ∩ courses across their own ACTIVE classrooms only; an admin's = the whole fleet (null collections). Deactivating a classroom drops it from the teacher's scope instantly (pivots/history untouched); reactivation restores it. Consumers take these scopes as OPTIONAL parameters (?Collection $studentIds, ?Collection $courseIds, ?array $studentCourseScopes) — null stays fleet-wide; a scoped student with an empty shared-course set is filtered OUT, never half-shown (StudentService::index uses this exact drop). ClassroomService is the only admin write path for classroom base fields + the teacher/student/course assignment sets; a status change never rewrites pivots; reassignment REPLACES the pivot set; every applied change AND every refusal records an AdminAuditService row; non-teacher ids in teacher_ids are refused at the REQUEST layer (Rule::exists + where role=teacher) before any write. Never rebuild the teacher/student/course overlap outside ClassroomAccessService.

## Report role checks precede retained classroom assignments
US-1012: changing a teacher's role can leave classroom teaching pivots intact. ReportAuthorizationService must require teacher/admin before delegating non-self student/course access or returning shared course IDs; student-self remains student-only. Unsupported roles return false/empty scope even with retained assignments. Keep this report-specific guard here; classroom membership remains owned by ClassroomAccessService. ReportSecurityTest covers retained assignments and export role boundaries.

## Classroom visibility requires current role and assigned scope
US-1102: only a current teacher may derive active classroom visibility from teaching pivots; retained assignments after a role change to student/operator confer no academic authority. Current admins retain the established fleet-wide exception. UserPolicy self-view grants academic data only to current students (or admins), not former teachers/operators.

## Academic writes use current server state
A student may submit evidence, never XP, verdict, completion, or unlock state. Gate mission and Knowledge Check writes on historical passes of earlier active courses; recheck course status at Boss submission. Lock and reload assessment attempts before state transitions, and serialize one-time XP purchases or awards against the user's current ledger state.

## Serialize student academic read-decide-write operations
For per-student XP spends, one-time rewards, and attempt/completion transitions, lock the authoritative user row before reading mutable state, then perform the decision and all database writes in one transaction. Keep the user-first lock order across related services; retain domain-specific unique constraints as backstops. Verify races with independent disposable MariaDB connections because SQLite does not reproduce row locks.
